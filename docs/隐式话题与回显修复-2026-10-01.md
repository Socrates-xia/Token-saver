# 隐式话题与回显修复（2026-10-01 · 第十轮）

> 触发：用户实测反馈 —— **"你新打开豆包生图的时候发出的对话带着咱们过往测试的
> 内容，就是很久前的对话。虽说不影响使用，不过感觉有点没必要。是不是粘贴的时候
> 出了些问题。"**
>
> 结论：不是粘贴环节的问题，是**回填**这一步出了两个 bug。用户"不影响使用"的
> 判断也对也不对 —— 错的答案确实会被当成功交付，只是那轮正好在生图、图的抓取
> 是对的。修复后版本 1.0.1。

---

## 一、现象与定位

用户看到的是"新开的生图窗口，发出去的提示词里带着很久以前的对话"。顺着
`CTX_HEADER` 里的"（下面是我们之前的对话记录…）"一搜，命中 `core/pool.py`，
再对账运行数据，元凶立刻现形：

```
auto-doubao:  10 轮历史，横跨 18 小时、三件毫不相干的事
  [0]  -1072 min  "请系统地列出中国的所有主要节日…"（2084 字）
  [1]   -105 min  嵌入式技术描述翻译
  [2]   -105 min  嵌入式技术描述翻译
  [3]    -23 min  "画一只奶龙，卡通风格"      ← a = 3618 字
  [4]    -22 min  "画一只橘猫，简笔画"
  [5]    -20 min  "画一只柴犬，卡通风格"      ← a = 6173 字
  [6..9]          熊猫 / 企鹅 / 老虎 / 四张柴犬
```

两处问题，一处比一处隐蔽。

## 二、根因

### 根因 A：隐式话题把不相干的任务粘在一起，又在会话断开时整段回填

`ask()` 里没给 `thread` 时会兜底挂到"该站点的隐式续聊话题"上：

```python
tid = f"auto-{resolved}" if (resolved and reset is None) else ""
```

设计意图是"连续追问自动连在同一个网页会话上"，但它**是按站点共享的一个键**，
于是几小时前、完全不同任务的对话全攒在 `auto-doubao` 里。而回填的唯一条件是
"网页会话没接上"（`live=False`），与新任务无关 —— 一旦浏览器上下文重建，
这 10 轮旧历史就被整段拼进提示词。

模块自己的 docstring 当时还写着"不带 thread 的调用视为一次性外包，每次都开
全新会话，互不污染" —— **代码与文档契约本来就已经不一致了**。

### 根因 B：回填块的文案把"回显判定"关掉了（更隐蔽）

对账时发现 `auto-doubao` 的 [3] 和 [5] 两条"答案"长这样：

```
a = '（下面是我们之前的对话记录。如果你在页面上已经能看到这段对话，
     就直接忽略它、回答最后的新问题）\n用户问：请系统地列出中国…'   len=3618
```

**"答案"就是我自己发出去的那段文本。** 逐层追下去：

1. `_ask_inner` 里本来有一道 `_bad()` 守卫，含 `looks_like_echo(a, prompt)`
   （"抓到的只是提问回显吗"）；
2. 但 `looks_like_echo` 里有条豁免：命中推理特征词就认作"深度思考在复述对话"、
   直接 `return False`；
3. 而 `_REASONING_MARKERS` 里含 **`用户问`**、`助手答`、`对话：`；
4. `_build_context()` 每轮拼的又恰好是 **`用户问：{q}\n你的回答：{a}\n`**。

两处文案一撞：**回填过的请求必然命中豁免** → 回显判定失效 → 生图轮（助手只出
图、文字回答迟迟不来）抓到的用户消息被当成答案收下，还写进话题历史；下一轮
回填把它带下去，于是 3618 → 6173 字，**自我放大**。

实测确认（拿真机记录下来的那条脏数据当夹具）：

```
looks_like_echo(a3, a3) = False      ← 答案和提问逐字节相同，却判"不是回显"
命中特征词：['用户问']
```

## 三、修法（4 处代码 + 2 处文档串）

| # | 位置 | 改动 |
|---|------|------|
| 1 | `core/adapter.py:looks_like_echo` | **两条"铁证"提到豁免之前**：① 归一化后逐字相同 ② 以原提问开头（说明抓回的容器把用户消息也包了进去）。顺带把重复的 probe2 判据合并进 ② |
| 2 | `core/pool.py:_build_context` | 回填块文案换词：`用户问：/你的回答：` → `【历史】上轮提问：/【历史】上轮答复：`，并注明"不许撞 `_REASONING_MARKERS`"这条硬约束 |
| 3 | `core/pool.py:_history_of`（新增） | **隐式话题恒返回空历史**。`auto-<站点>` 只借"网页会话还活着"这一件事，不借历史 |
| 4 | `core/pool.py:_try_one` | 隐式话题 + 网页会话没接上 → `sent, reset = prompt, True`，**干净开局**：既不回填，也不把问题发进那个残留着上一件事的旧会话页 |
| 5 | `core/pool.py:ask` | 交付前加**最后一道闸**：答案若等于本轮发出去的文本、或以回填块开头 → 直接判失败，绝不交付/记账 |
| 6 | `core/adapter.py:_ask_inner` | 生图轮例外：`_bad` 命中时不再硬失败，把 `answer` 清空继续走（**图才是这轮的交付物**），但"既无文字又无新图"仍如实报失败 |

顺带修的：

- `_append_message` 对隐式话题不再记账（免得 `threads.json` 越滚越大、还在控制台里骗人）；
- 日志措辞：隐式话题那行以前会打 `回填历史兜底`，现在打 `干净开局(隐式话题不回填)`；
- `pool.py` 模块 docstring 改成与实际行为一致的三条契约。

### 4.2 真机复验（新的 1.0.1 实例）

**① 豆包生图，不带 thread / reset**（就是用户报的那条路径）

```

reused_page=False  context_turns=0        ← 一轮历史都没回填
elapsed=35.18  via=... → dom(重等5次) +1图

```

网关日志：

```
[thread] 续聊 doubao: 复用页面会话=False | ctx重建=True |
  prev='331339934978' cur='ao.com/chat/' | 干净开局(隐式话题不回填)
```

`prev` 正是当年"列举中国节日"那个会话页 —— 修复前这里会把 10 轮旧对话整段发出去。

顺带一个**修复生效的直接证据**：`via` 里的 `dom(重等5次)` 说明首抓被 `_bad` 拦下
（那就是回显），程序又等了 5 轮才拿到真答案。修复前这里是"首抓即收工"。

**② 隐式话题的连续追问没被改坏**

```
第 1 问 "记住 5、8、13…"  →  reused_page=True  context_turns=0  8.47s  '记住了'
第 2 问 "第二个数字是多少" →  reused_page=True  context_turns=0  9.10s  '8'
```

靠网页会话本身接着问，答对了；**没有回填任何历史**（`context_turns=0`），
耗时也从 35 s 掉到 9 s。这条便利路径（省 token 的关键）完好。

**③ 账本不再被污染**

清空后连做 3 次调用（生图 1 + 追问 2），`auto-doubao.messages` 仍是 **0 轮**；
`yuanbao-关窗测试` 仍是 2 轮（点名话题照旧记账）。

## 五、影响面与残留

**受益**：所有"没传 `thread`"的调用（MCP 桥、控制台的即席提问、生图）。
不再出现"新窗口带着旧对话"，也不再可能把我方文本当答案交付。

**行为变化（唯一一条，需知会）**：隐式话题**不再有"会话丢了也能接上"的兜底**。
如果某一问依赖上文、又恰好赶上网页会话断开，它会干净开局而不是靠历史硬接。
要这个兜底就**显式传 `thread`**（点名话题的回填逻辑一字未改，元宝关窗自愈
那条链已复验通过）。这是刻意的取舍：隐式话题按站点共享，兜底带上的多半是
不相干的历史。

**未修（与本次无关，此前已记录）**：profile 停在旧会话上、且本轮助手只出图
不吐文字时，答案抽取器仍可能退回旧文字容器（图是抓对的）。复现条件苛刻、
改动波及其他站点，风险大于收益。规避办法：生图带 `reset: true`。

## 六、下次别再踩：两条通用教训

1. **文案撞车是真实的故障源。** 一处给"给模型看的提示词"，一处给"启发式判据
   用的特征词"，两边各写各的，撞上了就**静默关闭一道安全判定**。凡是"某段
   固定文案会被别处的正则/特征词消费"，就把它写成常量 + 加一条断言。
2. **判据的顺序就是语义。** 豁免/白名单类分支必须排在"铁证"之后 ——
   否则最该被抓的样本恰好被自己的豁免放过。修 bug 时先问："这条豁免会不会
   正好罩住出问题的那类输入？"
