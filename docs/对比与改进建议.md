# Token Saver vs GitHub 同类项目：对比与可改进点

调研日期：2026-09-30
对比对象：本机 `token-saver`（`WorkBuddy/2026-09-30-12-03-14/token-saver`）
参考仓库：`gasschina/zerotoken`、`linuxhsj/openclaw-zero-token`
（另参考 `Fly143/deepseek-free-api`、`davoodya/Deepseek-API-Free-Usage`、
`zhang588/deepseek-free-api`）

## 一、结论先说

`token-saver` 在**架构层面领先**参考项目，但有一处**技术代差**：

| 维度 | token-saver | 参考项目 | 谁更强 |
| --- | --- | --- | --- |
| 取答案方式 | 浏览器操作 DOM | 浏览器 / **纯 HTTP** | 参考项目 |
| 智能体定位 | **主动外包 + 成本判断** | 被动 API 网关 | token-saver |
| 成本决策 | 有（195 token 盈亏平衡） | 无 | token-saver |
| 中途叫停 | 有（文件哨兵 + 自动识别） | 无 | token-saver |
| 多轮上下文 | thread + 会话存活探测 + 失忆自愈 | messages 数组 | token-saver |
| 反脆弱 | 四级启发式 + 弹窗清理 + 站点自愈 | 选择器写死 | token-saver |
| 单站响应速度 | 7~15s（开浏览器） | 1~2s（纯 HTTP） | 参考项目 |
| 凭证管理 | `verify_session.py` | 一条命令全站登录 | 参考项目 |

**唯一的技术代差是"纯 HTTP 路线"**，已在本轮实现（见第五节）。

## 二、参考项目的三个可借鉴点

### 1. 凭证管理：一条命令登录全部站点

zerotoken 的 `zerotoken login --all` / `--list` / `--remove` 比逐个跑
`verify_session.py <站点>` 顺手得多，凭证统一落在
`~/.zerotoken/auth-profiles.json`（`0600` 权限）。

**可借鉴**：给 token-saver 加一个 `tools/login_all.py`，遍历已启用站点，
逐个 `open_login` + 轮询登录态 + `save_session`，最后打印一张
"哪家登录成功/失败"的汇总表。工作量小，收益明确。

### 2. 多账号轮换（参考项目也只是部分支持）

zerotoken 有 `listProfilesForProvider` 返回多份凭证的接口设计，
但实际只取 `profiles[0]`。真正做轮换的是 9router（`round-robin between
accounts per provider`）。

**可借鉴**：`data/state/<站点>.json` 改成支持多份凭据 + 轮询，
用于绕开单账号的日额度限制。**优先级低**——目前没撞到额度墙。

### 3. 明确声明"仅供学习研究"

参考项目 README 都写明了遵守各平台 ToS、不建议商用。
token-saver 的 SKILL.md 没提。**建议补一句**，属于合规自保。

## 三、token-saver 明显强于参考项目的地方（不必改）

这几处是独有的设计，参考项目完全没有对应物：

1. **成本判断闭环**。`router.complexity()` 给出
   `outsource / borderline / keep_local` 三档，配合"195 token 盈亏平衡"，
   让智能体**先算账再决定要不要外包**。参考项目只是"你调我就答"。
2. **中途叫停**。`killswitch` 用文件哨兵 + HTTP + MCP 三条通路，
   还能从"60 秒内浏览器被关 3 次"推断用户想停。
   参考项目关掉浏览器就等于放弃，没有等价机制。
3. **会话存活探测 + 失忆自愈**。`_looks_like_missing_ctx`
   （模型反问刚给过的信息）和 `_looks_like_topic_drift`
   （话题漂移，如问永城却答睢县）两个检测，抓出来就带历史重试。
   这套"我知道它可能忘"的自省是参考项目没有的。
4. **四级定位策略 + 弹窗清理**。厂商选择器 → ARIA → 几何启发式 → 剪贴板，
   任一级命中即停；入场弹窗按 Esc → 站点选择器 → 文案启发式 → 点遮罩
   四级清理。参考项目靠写死选择器，改版即挂。
5. **抓答案的两条净化链**。`strip_noise` 处理引用角标、检索状态行、
   UI 尾巴；`TABLE_TO_MD_JS` 把 `<table>` 还原成 Markdown、
   从 MathML 里抢救 TeX 源码。参考项目直接取纯文本，表格和公式会散架。

**这些是护城河，不要为了"对齐参考项目"而稀释。**

## 四、纯 HTTP 路线：唯一值得动手的代差

### 为什么值得做

浏览器路线的固定成本太高：

- 冷启动要起 Edge、加载页面，**7~15 秒**才出第一个字
- `SKILL.md` 里的盈亏平衡点是 **195 token**——这个数字被延迟拖着
- 换成纯 HTTP 后，往返降到 **1~2 秒**，盈亏平衡点可以下压，
  更多小任务变得值得外包

### 协议（已逆向确认）

DeepSeek 的 `/api/v0/chat/completion` 有两道闸门，第二道是纯计算题：

```
POST /api/v0/chat/create_pow_challenge
  body: {"target_path": "/api/v0/chat/completion"}
  → challenge = {
      algorithm:  "DeepSeekHashV1",
      challenge:  "<64 hex>",
      salt:       "<20 hex>",
      difficulty: <int>,
      expire_at:  <ms 时间戳>,
      signature:  "<hex>"
    }

answer = wasm_solve(challenge, f"{salt}_{expire_at}_", difficulty)

请求头：x-ds-pow-response = base64(JSON({
    ...challenge, answer, target_path: "/api/v0/chat/completion"
}))
```

`wasm_solve` 来自 DeepSeek 官方前端那份 `sha3_wasm` 模块。把它跑起来
就完全绕开了浏览器。

### 本轮已完成

| 文件 | 作用 |
| --- | --- |
| `tools/extract_sha3_wasm.py` | 从参考仓库源码里抽出内嵌的 WASM（base64 → 二进制） |
| `data/sha3_wasm.wasm` | 26,612 字节，已验证含 `wasm_solve` 等 4 个符号 |
| `core/pow_deepseek.py` | 求解器 + 自检 + 真接口验证入口 |

自检结果（`python core/pow_deepseek.py`，退出码 0）：

```
1) WASM 加载: ok
2) 求解: ok（0.028s，answer=58033）
3) 响应字段: ok
4) 连续 5 次复用: ok（栈指针无泄漏）
```

依赖：`wasmtime`（已装进 `envs/tokensaver`）。

### 踩到的两个坑（都已修，且已在代码里注明）

**坑 1：前缀末尾必须带下划线。**
`f"{salt}_{expire_at}"` 不行，必须 `f"{salt}_{expire_at}_"`。
少一个下划线，WASM 会一路算到上限返回 `status=0`，
报出来的却是"未找到解"，极具误导性。

**坑 2：WASM 栈指针必须无条件归位（这个坑更深）。**
`__wbindgen_add_to_stack_pointer(-16)` 借的栈空间，**必须在
`finally` 里还回去**。只在成功分支还的话，每次失败永久漏 16 字节；
实测连续几次失败后 `retptr` 一路 `1048560 → 1048544 → 1048528`
递减，最终写出界踩坏 WASM 内部状态——**此后连本来能解的挑战也一律返回 0**。
我第一版就是这么写的，症状是"第一次能解、之后全失败"。
现在用 `try/finally` 兜住，并加了"连续 5 次复用"的回归测试。

另有一个次要点：`memory.grow` 会让 `data_ptr` 失效（实测第二次
`malloc` 触发 17→18 页增长）。所以**分配与写入必须成对，写入前重新取指针**。

### 一个诚实的限制（重要）

`challenge` / `salt` / `difficulty` 是**服务端签发的配套三元组**，
WASM 内部有一致性校验。我实测过：拿官方样例的 `challenge`+`salt`
配不同 `difficulty`，只有 `65536` 能解出 `answer=58033`，
其他值（1、16、256、4096、144000、1000000）**全部瞬间返回 0**。

结论：**用合成数据无法验证求解器，必须打真接口。**
所以模块提供：

```bash
python core/pow_deepseek.py --live <cookie> [bearer]
```

真实验证需要你的登录态，本轮没跑（不该拿你的凭据做未授权的联网请求）。
自检只证明"模块加载 + 调用约定正确"，这一点在代码注释里写清楚了，
避免以后误以为自检通过就等于能解任意挑战。

### 下一步（建议分两阶段）

**阶段一（低风险，可先做）**：只让 **DeepSeek 一家**走 HTTP。
`core/adapters/deepseek.py` 里加一条"优先试 HTTP，失败退回浏览器"的路径。
其余站点保持现状。这样风险面最小，且 DeepSeek 是当前 priority 最高
（30）的站点，收益最直接。

> **✅ 阶段一已完成（2026-10-01）** —— 见文末"阶段一实现记录"。

**阶段二（视效果）**：把相同的 PoW 思路推广到其他站点。
从调研看，豆包 / Kimi / 元宝 各家都有自己的风控（豆包要 `ttwid`、
Kimi 走 `access_token` cookie），但**都不是 PoW 这种纯计算题**，
需要各家单独逆向，投入产出比明显低于 DeepSeek。

**注意**：纯 HTTP 会绕过网页端的一些反爬机制。参考项目都声明了
"仅供学习研究、遵守 ToS"。建议在做阶段一之前先明确这个定位。

## 六、一句话总结

`token-saver` 的**智能体语义和反脆弱设计明显强于** GitHub 上的同类项目，

### 设计要点

1. **HTTP 分支必须放在 `ensure_page()` 之前**。放后面就没意义了——
   浏览器已经起来，7~15 秒的固定开销已经花掉。

2. **`ask_http()` 任何失败都返回 `None`**，从不抛异常给上层。
   HTTP 是加速路径不是必经之路，不能因它的失败影响可用性。

3. **凭证两级来源**：Cookie 优先从 `data/state/deepseek.json`
   （浏览器路线早就在存）读，所以**第一次就可能直接走通**；
   Bearer 只在 localStorage 里，必须靠活页面收一次。
   401 时自动作废缓存 → 退回浏览器 → 顺手重收，全自动自愈。

4. **会话复用对齐浏览器语义**：`reuse_session=False`（失忆自愈的重试
   就传这个）时，HTTP 也会新开会话并把历史补进去，否则重试等于白试。

5. **HTTP 结果要跳过"答案是上一轮的那份"检查**。那条检查是为浏览器
   路线写的（重读页面可能读到旧内容）；HTTP 的答案来自本次 SSE 流，
   天然是新的。不区分的话，同一话题连着问同一句话会被误报成失败。

### DeepSeek SSE 协议实况（2026-10-01 抓真流确认）

文档里猜字段名会一直猜错，这一节是真流 dump 出来的结论，**改解析器前先看这里**。

整条流只有三类事件：

```jsonc
// ① 片段元数据：没有 p 字段，v 是一整个 response 对象
{"v": {"response": {"message_id": 2, "fragments": [
    {"id": 2, "type": "THINK", "content": "我们需要", "stage_id": 1}]}}}

// ② 显式路径事件：宣告"接下来往哪儿写"
{"p": "response/fragments/-1/content", "o": "APPEND", "v": "回答"}

// ③ 裸增量：只有 v、没有 p，承接**最近一次显式声明的路径**
{"v": "用户"}  {"v": "中文"}  {"v": "问题"}  …
```

片段切换：

```jsonc
{"p": "response/fragments/-1/elapsed_secs", "o": "SET", "v": 0.41}   // 思考结束
{"p": "response/fragments", "o": "APPEND",                            // 追加新片段
 "v": [{"id": 3, "type": "RESPONSE", "content": "1", "stage_id": 1}]}
{"p": "response/fragments/-1/content", "v": "+"}                      // 无 o，也是增量
```

开联网检索时还会多两种形态：

```jsonc
// 批处理 + 相对路径：子事件的 "content" 要拼上父路径
// → response/fragments/-1/content（-1 此刻指向 TOOL_SEARCH）
{"p": "response/fragments/-1", "o": "BATCH", "v": [
    {"p": "status", "v": "FINISHED"},
    {"p": "content", "v": "搜索到 10 个网页"}]}
```

实测片段类型表：`THINK`（思考）、`RESPONSE`（正文）、
`TOOL_SEARCH` / `TOOL_OPEN`（工具片段，内容是界面状态，**整类丢弃**）。

### 本轮修掉的坑（都有回归测试）

- **裸增量被误当正文**（最隐蔽的一个）。真实流里绝大多数增量是
  `{"v": "…"}`，没有 `p`。它靠"承接上一条显式路径"决定归属；
  单看一行它长得就像正文，于是**整段思考被倒进答案**、而且不报错。
  必须维护一个 `cur_path` 状态。
- **新片段是靠 `p=response/fragments` 追加的**，不是走元数据事件。
  不登记这条，`-1` 永远停在旧片段上，归属全错。
- **片段类型字面量是 `THINK`**，不是 THINKING / REASONING。
- **`-1` 对思考和正文是同一个值**，只能靠片段类型判归属。
- **工具片段（`TOOL_*`）也带 content**。不单独剔除的话，答案开头会多一句
  "搜索到 10 个网页"。
- **BATCH 子事件用相对路径**。不拼父路径的话，`"content"` 会退化成普通
  正文路径，工具状态就混进答案了。
- **不能对片段内容套"累计快照"启发式**。真实服务端发的是增量，
  启发式会把 `"1"` + `"1"` 误判成快照，答案里的 `1+1` 变成 `11`。
- **`create_session` 不能带 PoW**，带了会被拒 `INVALID_TARGET_PATH`
  （服务端只给 `/api/v0/chat/completion` 签挑战）。现象是"配好了却
  始终走浏览器"，日志里只有一句 `INVALID_TARGET_PATH`。
- **直连的引用角标是方括号形态**（`[reference:0]`），和网页端渲染出的
  `-11` 不是一套写法，两种都得清。
- **`thinking_content` 里同时含 "thinking" 和 "content"**，
  判定顺序写错会把整段思考混进答案。
- **PoW 求解器的前缀必须以 `_` 结尾**，且 `wasm` 栈指针要在
  `finally` 里还回去（否则失败一次漏 16 字节，攒够了连可解的题都解不出）。
- **`status()` 少了 `enabled_globally`**，工具里显示成 `None`。

- 两处副本（开发副本 + skill 包的 `gateway/`）均已同步，且**在技能包自己的

## 八、第二轮：追问链路上挖出的三个坑（2026-10-01）

拿直连连着追问了 6 轮（话题 `soup-health`），一路都在"看起来正常"的状态下
静默烧钱。三个坑的共同点：**都不报错，只是多花时间、多花 token，而且只在
特定的调用序列下才现形**。

### 坑 1：会话记录一直在写，却从来没被读回来过

```python
def _load_sessions() -> None:
    global _sessions_loaded        # ← 漏了 _sessions
    if _sessions_loaded:
        return
    _sessions = _load_json(SESSION_FILE)   # ← 赋值给了**局部变量**
    _sessions_loaded = True
```

漏写 `global _sessions` 的后果：加载结果只落到局部变量上，模块级 `_sessions`
永远是空的。单进程内完全看不出来 —— `remember_session` 是
`_sessions[tid] = ...` 这种原地修改，改的是真家伙，所以同进程内追问一切正常。
**但网关一重启，所有会话续接静默失效**：之后每次追问都重开会话、回填整段历史，
恰好把直连该省的 token 又花回去。

发现方式：重启后第一次追问的日志里出现了
`新建会话 … / 新会话，回填 3086 字节历史`，而上一轮明明是"接上文=True"。

修法：`global _sessions_loaded, _sessions`。

> 附带一课：`pool._load_threads()` 用的是 `_threads.update(...)`（原地修改），
> 所以它同样只声明了 `global _loaded` 却没问题。**同样的写法，赋值会坏、
> 原地修改不会坏** —— 这就是它当初没被发现的原因。

### 坑 2：自愈重试没把 `thread` 传下去

```python
retry = await _try_one(a, prompt, reset=False, ...,
                       reuse_session=False)          # ← 少了 thread=tid
```

重试会**新开一个远端会话**，但不传 `thread` 时 `http_deepseek` 就不会
`remember_session` —— 新会话等于白开：话题指针还停在那个"模型没接上上文"的
旧会话上，下一次追问又去接它，历史还得再回填一遍。

修法：补上 `thread=tid or ""`。

### 坑 3：`resumed` 算错 → 重试反而不回填历史

```python
resumed = bool(parent) or bool(session_for(thread).get("session_id"))
```

这句问的是"**这个话题在库里有没有会话记录**"，而不是"**这一轮真的接上了吗**"。
`reset=True` 时（重试路径就是这么调的）话题记录依然存在 → `resumed` 被判为真
→ **跳过历史回填** → 重试等于在一个空白会话里又问了一遍，上下文全丢。
自愈重试的答案反而更差，根子就在这。

修法：只认"这一轮的 session_id 是从库里取来的"。

```python
resumed = False
if not reset and thread:
    ...
    resumed = bool(session_id)
```

### 坑 4：跑题检查拿到了正确的输入吗？（连续误报两次）

`_looks_like_topic_drift` 靠"上文高频词在答案里一个都没出现"判断答错对象。
它在长答案上会退化（挑出的"话题特征词"全是 markdown 残渣 `"。\n\n"`、`"\n**"`，
判定等于在比"两个答案的排版像不像"），于是：

- 第一次误报：换个排版就判跑题 → 白扔一整次调用；
- 修了长度阈值（`_DRIFT_PREV_MAX = 600`）后**又误报一次** ——
  因为调用方传进去的根本不是全文，而是 `prev_answer`（上一轮答案的
  **末尾 60 字**，那是给浏览器路线比对页面残留用的），60 < 阈值，
  长度保护形同虚设。

修法：新增 `prev_full`（全文）专供跑题检查，`prev_answer`（60 字尾巴）
继续留给浏览器路线的比对；并在函数 docstring 里写死调用契约。

### 顺带清掉的噪声

DeepSeek 会在答案末尾**不带换行**地粘一句
"本回答由 AI 生成，内容仅供参考，请仔细甄别"，按行丢弃处理不掉，
只能按结尾锚点剥（`_AI_DISCLAIMER_RE`）。

### 新增回归测试

`tools/selftest_thread.py` —— 10 项，离线、不联网、不耗额度。
专测两个"失败方式都是静默"的判定函数（误报＝白烧一次调用，
漏报＝交付跑题的答案），其中长上文用例、以及
"pool.ask 必须喂全文"的契约检查，都直接来自真机踩坑。

`tools/test_http.py` 增至 **30 项**，新增会话持久化的跨进程读取用例
（模拟"刚启动的进程"，把内存缓存清空，验证能从磁盘读回会话）——
这条正好能抓住坑 1。

```

[http] deepseek 直连成功：10.16s、483 字、接上文=True
```

## 九、第三轮：元宝"回答被腰斩"——一个坏了两个月的 JS 字符串（2026-10-01）

用户要求实测元宝的追问模式，并中途人为干扰页面。**干扰测试本身通过了**
（关掉浏览器窗口后网关自愈，追问 `continued: true`），
但同一轮里暴露出一个更严重的问题，顺藤摸瓜挖了四层。

### 坑 1：答案选择器里用了 CSS4 复杂否定，在本机 Chromium 上静默失效

元宝的思考过程和正文答案**共用同一套 markdown 类名**，只能靠所在面板区分。
原代码想用一句话解决：

```css
div[class*='markdown']:not(.hyc-component-deepsearch-cot *)
```

实测这个选择器在当前 Chromium 上**命中 0 个元素**，而且不报错 ——
Playwright 不会告诉你"这个选择器没人支持"，它只是安安静静地返回空。
于是这个"首选选择器"等于不存在，一路落到泛选择器 `[class*='markdown']`，
思考过程照样被抓回来。

退化写法 `:not(.hyc-component-deepsearch-cot)` 能命中，
但那只排除元素**自身**，排不掉它的子孙 —— 思考面板里的 markdown 照样漏进来。

**正解**：选择器只管"命中哪些类名"，"哪些不算答案"交给
`answer_exclude` + JS 的 `closest()` 判断（新增的站点级配置项）。

### 坑 2：排除范围搞错 —— 把"整条消息的外壳"当成了"思考面板"

换成 `answer_exclude` 之后第一次仍然失败，而且失败得更隐蔽：
`snapshot_answer()` 从此**永远返回空字符串**，一路等到 `ask_timeout`。

原因：`.hyc-component-deepsearch-cot` 不是思考面板，是**整条 AI 消息的外壳**，
思考块和正文答案是它内部两个平级的子块。判据很直白：

```
外壳 innerText 长度 2462 ≈ 思考 1390 + 答案 1058 + 14
```

排掉整壳 = 连答案一起排掉。正确目标是 `...-cot__think` 这一层。

外层看到的现象只是"超时"，要**白等 240 秒**再退到别的站点从头重来一遍，
日志上只留一句超时 —— 从日志根本猜不到是选择器的事。

→ 为此加了**防呆** `_check_exclude_sanity()`：
连续 30 秒"有候选但全被排除"就主动抛错，并在错误信息里点名
"多半是把整条消息的外壳当成了思考面板"。

### 坑 3：★ 根因 —— `TABLE_TO_MD_JS` 里的注释把整个 JS 语法搞崩了

写完回归测试跑第一次，`page.evaluate(PICK_ANSWER_JS, ...)` 抛
`SyntaxError: Invalid or unexpected token`。

一路回查，发现**老代码里的 `TABLE_TO_MD_JS` 有同样的问题，而且一直没被发现**：

```python
TABLE_TO_MD_JS = """
...
    //   · 它渲染出来的文本是 "-\n20"（短横与数字之间**夹着换行**），
"""
```

这是**普通**三引号字符串，那个 `\n` 会被 Python 先解释成一个真换行字符 ——
`//` 注释被劈成两行，第二行开头露出一段没被注释掉的残句
（`20"（短横与数字之间**夹着换行**），`），整个 JS 直接语法错误。

Python 侧完全看不出问题（字符串本身完全合法），只有真拿 JS 引擎解析才会暴露。

**为什么两个月没人发现**：调用方写的是

```python
try:
    txt = await cand.evaluate(TABLE_TO_MD_JS)
except Exception:
    txt = await cand.inner_text(timeout=1500)      # ← 静默降级
```

异常被吞掉、优雅退回 `innerText`，结果"看起来也像那么回事"。
代价是三件事**从来没有生效过**：

| 声称的功能 | 实际状态 |
|---|---|
| `<table>` → Markdown 表格 | 从未生效，表格被拉成一行行文字 |
| 数学公式 → 还原 TeX 源码 | 从未生效，上下标变成 `3.3 V212=3.34096` 这种乱码 |
| 在 DOM 层摘掉引用角标 | 从未生效，只能靠较弱的文本正则兜底 |

**修复（三件事一起做，缺一不可）**：

1. 把这段 JS 抽成**单一来源** `_TO_MD_JS`，用**原始字符串** `r"""` 包起来，
   里面的 `\n` / `\|` 原样交给 JS；
2. `TABLE_TO_MD_JS` 和 `PICK_ANSWER_JS` 都由它拼接而成，杜绝"抄一份、改一处"；
3. 调用方**不再静默吞异常**：错误记进 `answer_pick`，
   连续 30 秒抛错同样主动报错（`_check_eval_sanity` 合并在同一函数里）。

只做第 1 件，下次换个写法还会重演；只做第 2、3 件，故障至少能立刻暴露。

### 坑 4：答案元素被"最外层容器里的最后一块"顶掉

`[class*='markdown']` 会同时命中外层答案容器**和它内部的每一个子块**
（元宝的表格包裹层 `hyc-common-markdown__table-wrapper`）。
老代码取"最后一个命中"，于是拿到的是表格包裹层：

```
#0 顶层  len=3084  思考面板
#1 嵌套  len=70    表格包裹层（流式中间态）
#3 顶层  len=1104  ★ 真正的答案容器
#4 嵌套  len=792   表格包裹层（最终态）
```

拿 `#4` 而不是 `#3`，答案前半段（"核心要点"整节）**静默丢失**。
更糟的是流式过程中表格单元格先是省略号占位，这段文字能连续稳定好几秒，
而"文本稳定 N 秒即完成"正是判完成的依据 → 当场收工，只捞回一行表头（66 字）。

**修复**：只保留**最外层候选**（不被其他候选包含的），再取最后一个。
对 DeepSeek / 豆包 / Kimi 是**零行为变化** —— 它们的答案本来就是顶层命中，
`tops` 的末位就是它本身；只有末位是被包住的子块时结果才会变。

### 真机时序（`tools/probe_yuanbao_live.py` 采样）

新增的时序采样器把"文本长度随时间怎么变"和"当时有没有停止按钮"对齐后：

```
[  11.0s] cot=64      顶层[60]          ← 思考过程开始流式（被排除，抓不到）
[  19.5s] cot=1145    顶层[1141]        ← 思考仍在长
[  21.9s] cot=1454    顶层[1390,50]     ← ★ 答案容器出现，第二个顶层候选
[  25.6s] cot=1880    顶层[1390,476]    ← 答案在长，思考已冻结
[  30.4s] cot=2462    顶层[1390,1058]   ← 答案完成
[  31.7s] cot=2462    顶层[1390,1058]   ← 连续稳定
```

两个关键事实：

- **元宝全程没有"停止"按钮**（`stop_buttons` 每一次采样都是空）。
  也就是说完成判定**完全依赖"文本稳定 N 秒"**这一个判据 ——
  这也是坑 4 里"抓到半截表格就收工"能被触发的根本原因。
- 思考过程被正确排除后，答案出现前 `snapshot_answer()` 返回空字符串，
  "文本稳定"计时不会启动 → 顺带把"思考刚结束就误判完成"这个老问题也堵住了。

### 新增回归测试

`tools/selftest_answer_pick.py`（17 项，不联网、不消耗额度）：

- **JS 语法守门**：把三个内嵌 JS 常量丢给 `node --check` 过一遍。
  这是全仓库最值得保留的一条 —— Python 侧语法完全正确，
  任何 Python 检查都发现不了坑 3，只有真的拿 JS 引擎解析才行。
- **DOM 用例**（headless Edge + `set_content`）：复刻元宝真实 DOM 形状，
  锁定"表格包裹层必须被过滤""排掉整壳会全军覆没""答案不能含思考过程"。
- **源码契约**：禁止在 `selectors.answer` 里出现 CSS4 复杂否定；
  `_check_exclude_sanity()` 必须在两个轮询循环里都被调用。

用 `kind=text`（按文字找元素 + 返回祖先链）一查，层级是这样的：

<div class="hyc-common-markdown ...">          ← 我们的选择器命中的答案容器

顺带验证：站点"复制"按钮给的 Markdown 原文里**没有**这个卡片，
所以走剪贴板那条路本来就不受影响 —— 只有 DOM 路线需要这份名单。
这一点也写进了 `answer_strip` 的注释，免得将来有人以为两条路都要改。

## 十一、第五轮：并行外包（同任务拆多部分，多家同时做）（2026-10-01）

### 起因

到这一轮为止，token-saver 是"一家一家问"：N 个部分 = N 段串行等待。
但每家站点本来就是**独立的浏览器上下文**（各自一个 persistent context + page），
彼此之间没有任何共享状态 —— 天然可以并行。用户的直觉很直接：
"同任务不同部分，分配多个不同的网页端 AI 去同时完成，提高效率。"

### 已有的并发基础（一行没改）

| 事实 | 位置 | 含义 |
|---|---|---|
| `pool.ask` 里**没有全局锁** | `core/pool.py` | 不同 provider 可以同时在跑 |
| `async with browser.manager.lock(a.id)` | `core/pool.py::_try_one` | **同一家**自动串行，一条车道里排多个部分是安全的 |
| 纯 HTTP 路线在拿锁**之前**就 return | `core/http_deepseek.py` | DeepSeek 压根不占车道，同家跑多部分也不冲突 |

顺带纠正一个早期误判：我一开始用关键词 grep 找锁，没匹配到，以为是"还没有并发基础、
要大改"。实际上锁早就在了，只是名字跟我猜的不同。**先读代码再下结论，别用 grep 的
命中率当证据。**

### 车道模型

```
部分1 ─→ 车道A（元宝）    ─┐
部分2 ─→ 车道B（豆包）     │
部分3 ─→ 车道C（DeepSeek） ├─ asyncio.gather ─→ 按编号合并
部分4 ─→ 谁先空谁领        │
部分5 ─→ …                ─┘
```

**一条车道 = 一家站点 = 一个可见浏览器窗口。** 同一车道内的多个部分**串行**执行 ——
这不是性能妥协，而是正确性要求：一个站点只有一个页面，两份内容同时打进去会把
网页端会话搅乱。**想提高并发就加车道（多登录一家），而不是给同一家加压。**

### 领活方式：默认"谁快谁多干"

真机实测的速度差是这一轮所有设计的根源：

| 站点 | 路线 | 单段耗时 |
|---|---|---|
| DeepSeek | 纯 HTTP 直连 | 1.3 ~ 2.6 秒 |
| 豆包 | 开浏览器 | 20 ~ 21 秒 |
| 元宝 | 开浏览器 | 23 ~ 28 秒 |

**差 10 倍以上。** 所以默认 `schedule="dynamic"`：所有部分放一个 `asyncio.Queue`，
每条车道循环 `get_nowait()`，谁先做完谁领下一个；`roundrobin` 保留为
"开跑前平均分好"，用途是**刻意均摊**（不想把某一家的额度打光）。

同一份 6 段 / 3 车道的翻译任务，同一批站点，只换调度：

```
dynamic     墙钟 27.85s  {'yuanbao':[1], 'doubao':[2], 'deepseek':[3,4,5,6]}
roundrobin  墙钟 50.93s  {'yuanbao':[1,4], 'doubao':[2,5], 'deepseek':[3,6]}
```

**墙钟 50.93s → 27.85s，快 1.83 倍。** 逐段译文都正确、无串扰，`retried=0`。

### ★ 这一轮最重要的认知：墙钟下限是"最慢那家跑一段的时间"

27.85 秒**正好等于**元宝单独跑一段的耗时（27.85s）—— 也就是说，动态调度
**已经把这个配置压到了理论下限**，再优化也快不了。含义有三条：

1. 继续把活拆成 10 段、20 段**不会更快**，因为元宝光跑一段就要 28 秒；
2. 想更快只有两条路：**多登录一家快站点**（尤其能走 HTTP 直连的），
   或者**不让慢站点上车**（`providers` 里只写快的）；
3. `speedup`（相对串行的加速比）这个指标**在不同分配方案之间不可直接比较** ——
   分母 `sequential_estimate` 本身就是各部分耗时之和，分配变了它就变了。
   跨方案比较只有 `wall_clock` 是诚实的。这一轮差点被
   `speedup 1.87 → 1.99`（看着只涨了 6%）骗过去，其实墙钟砍掉了 45%。

### 挖出并修掉的坑

| # | 问题 | 为什么会发生 / 危害 | 修法 |
|---|---|---|---|
| 1 | `note_rebuild()` 对**首次启动**也计数 | 停机保护是"60 秒内重建 3 次→停机"；并行拉起 3 家正好凑够 3 次，**第一次并行就会被自己停机**。这也是潜伏 bug：三家兜底链本来就会误停机 | 只在 `self._page.get(pid) is not None`（真重建）时计数 |
| 2 | `fanout` 没传 `reset` | 同家的多个部分被网页端当成**同一话题的连续追问**，第二部分把第一部分的答案当历史带上（实测回填 **2264 字节**）。看起来完全正常，只是悄悄多烧钱+串扰 | 强制 `reset=True` |
| 3 | 补跑成功后没从**原车道**摘掉该部分 | `assignment` 里同一个编号同时挂在两家名下，看上去像"这段被跑了两遍"，而且 `assignment` 不再是 parts 的划分 —— 报告就不敢信了 | 补跑成功时先从 `taken[prev]` 里移除 |
| 4 | `schedule` 不校验，不认识就当默认 | 有人写 `"roundrobin "`（多半空格）会被**静默**当成 dynamic，"我要刻意均摊"的意图悄悄落空 | 归一化（strip+lower）+ 未知值明确报错并列出可用取值 |
| 5 | 自检脚本"不联网"却**真的开了元宝浏览器** | 新加的 `schedule` 归一化用例直接调了 `fanout.fanout()` 而没打桩，真的拉起浏览器问了句 "X" | 一律走 `run_fanout()` 桩 |

### 测试替身的教训（值得单独记一笔）

第一版 `selftest_fanout.py` 的假 `pool.ask` 签名是
`(prompt, *, provider, timeout, fallback)` —— **漏了 `reset`**。
于是 `fanout` 传进来的 `reset=True` 直接抛 TypeError，被 `do_part` 里的
`except Exception` 变成"这个部分失败了"。测试没测到调度，反而像是我把调度写错了。

同一轮还有第二发：为了测降级路径，我给假 `ask` 加了"车道 b 在 fallback=False 时必失败"，
结果它**污染了所有用例** —— 主用例里第 2、5 段被补跑，`assignment` 出现重复编号，
看起来像真实 bug。改成 `fail_lanes=()` 默认空、只在该用的用例里显式传，才干净。

**结论：假替身的接口漂移，以及替身里"到处放火"的默认行为，是这类测试的头号假信号。**
所以那两条教训直接写进了 `selftest_fanout.py` 的 docstring 和 `SKILL.md`。

### 附带的小基建：`POST /api/shutdown`

以前改完代码重启只能硬 `taskkill` python 进程，结果是 Playwright 拉起来的 Edge
变成孤儿进程继续占着 `data/profiles/<站点>` 的 profile 锁，下次启动报
"profile 被占用" —— 而且因为**只有一个内核的错误被显示**，还容易被误读成
"没装浏览器"（内核回退那段的报错问题在上一轮修过）。

新端点先 `close_all()` 关干净浏览器、再 `os._exit()`，不留尾巴：

```bash
curl -s -X POST http://127.0.0.1:8787/api/shutdown -d '{"code":0}'
```
