## 二、逻辑 bug（已实机复现，建议优先修）

### 5. ★ 停机后删 `data/STOP` **无法恢复**

`KillSwitch.reason` 是常驻内存的，`halted()` 只读 `self.reason`；
删掉哨兵文件后内存里的 reason 还在 —— 而**代码和文档共 6 处**都在教用户
"删掉 `data/STOP` 即可恢复"。

实测（2026-10-01，对本机运行中的网关）：

```
1) POST /api/stop           → {"halted": true, "reason": "验证用"}
2) rm -f data/STOP
3) GET  /api/status         → {"halted": true, "reason": "验证用"}   ← 文件没了还在停机
4) POST /api/ask            → "[已停机] 验证用"
                              hint: "要继续就删掉 data/STOP 或调用 resume。"  ← 死循环
5) POST /api/resume         → 才恢复
```

**用户视角**：照提示删了文件，程序还是不动，而且还在叫他再删一次。

要改的 6 处文案/行为：

| 文件 | 行 | 现状 |
|---|---|---|
| `core/killswitch.py` | 100 | note_rebuild 的停机原因 |
| `core/browser.py` | 119 | context() 抛错文案 |
| `core/pool.py` | 580 | ask 的 hint |
| `core/pool.py` | 661 | 全失败时的 hint |
| `mcp_bridge.py` | 278 | stop_offload 返回文案 |
| `SKILL.md` §七 / `references/troubleshooting.md` | — | 同 |

**两种修法（择一）**：

- **A（推荐，让文档成真）**：`halted()` 在查哨兵时，若"文件不存在 **且** 当前 reason
  是我们自己落过盘的" → 就地 `clear()` 并返回空。这样"删文件即恢复"成立，
  也符合"文件哨兵是最土的看门狗"这个设计意图。
- **B（最省事）**：所有文案改成只留 `POST /api/resume`，去掉"删文件"这条。

### 6. ★ fan-out 的 `label` 参数**完全失效**

```python
# core/fanout.py::_merge
head = label.format(n=r["n"], total=r["total"])
#                         ^^^^^^^^^^^^^^^ 先取这个键 → KeyError
```

生产代码 `do_part()` 写入的 dict **从来没有 `total` 这个键**，于是
`r["total"]` 先抛 KeyError，被 `except Exception` 兜底成 `f"第{r['n']}部分"` ——
**任何自定义 label 都被静默忽略**。

实证：上一轮真机跑 fan-out 时请求里写的是 `"label": "第{N}块"`，
返回的 `merged` 却是 `## 第1部分` —— **输出就在眼前，我当时没逐字对照，漏了。**

**修法**：`do_part()` 里补 `"total": len(parts)`（一行）。

### 7. ★ 自检脚本对 6 号是**假绿**

`tools/selftest_fanout.py` 的合并用例：

```python
results = [
    {"n": 1, "total": 3, "ok": True, "answer": "答案一"},   # ← 手写的 total
    ...
]
check_true("自定义 label 生效", "## 片段1" in _merge(results, "sections", "片段{n}"))
```

测试数据**手写了 `total`**，而生产代码不产生这个键 → 测的是一个不存在的形状。
所以"自定义 label 生效"一直显示 ✓。

**修法**：合并用例的数据用**生产同款构造**（跑一遍真 `fanout()` 拿 `results`），
或至少补一条"`_merge` 的输入必须含 `total`"的形状断言。

> 这是同一类错误的**第二次发作**：上一轮是假 `pool.ask` 签名漏了 `reset`。
> 教训：「测试通过」之后要再问一句 —— **测试用的数据形状，和生产一致吗？**

## 三、安全加固

### 8. ★ CORS `allow_origins=["*"]` + 零鉴权

```python
app.add_middleware(CORSMiddleware, allow_origins=["*"],
                   allow_methods=["*"], allow_headers=["*"])
```

网关监听 `127.0.0.1:8787`、**没有任何鉴权**。这意味着：

- 你浏览的**任意网页**都能 `fetch('http://127.0.0.1:8787/api/threads')`，
  而该接口返回**全部历史问答正文**（实测返回里有完整的中英文对照内容）；
- POST 端点可被跨站触发：`/api/stop`、`/api/resume`、`/api/shutdown`、`/api/stats/reset`、
  `/api/ask`、`/api/fanout`、`/api/providers/{pid}/login`。
  注意：CORS 只拦"读响应"，**拦不住"发请求"** —— 简单请求的副作用照样发生。

**修法**：控制台是同源（同一个 8787），**根本不需要 CORS** → 直接删掉这段中间件。
若要给别的端口的前端用，就把 `allow_origins` 收成具体来源。

### 9. `ensure_page()` / `close()` 不在 per-site 锁内

`pool._try_one` 里有 `async with browser.manager.lock(a.id)`，但 **`server.py` 的 6 个端点
没有持锁**：`/api/providers/{pid}/login`、`/api/providers/{pid}/restart`、
`/api/debug/dom`、`/api/images`、`/api/debug/dismiss-popup`、`/api/debug/click`。

与在飞的 `ask` 撞车时，两边都会判定"页面失效"→ 各自 `_drop()` 后对**同一个
`user_data_dir`** 调 `launch_persistent_context` → 第二个报
`user data directory is already in use`（正是 `browser.py` 里那段报错文案描述的情形）。

触发概率不高（要同时在飞），但**调试时很容易踩** —— 一边批量跑、一边点控制台排障。

**修法**：给这些端点包一层 `async with browser.manager.lock(pid):`。

> 附带：`pool.availability(force_check=True)` 里那处 `ensure_page` 也漏锁，
> 但全库无人以 `True` 调用它，属死代码，可一并处理或删掉。

### 10. `_pick_lanes()` 不检查 `enabled()`

```python
if providers:
    lanes = [by_id[p] for p in providers]     # ← 没有 a.enabled() 过滤
```

指定 `providers: ["kimi"]` 时，即使 kimi 已停用，**仍然会打开 kimi 的浏览器窗口**。
（自动挑车道那条路是过滤了的，两条路行为不一致。）

### 11. 控制台没有任何停机入口

`web/index.html` 里 grep `/api/stop`、`/api/resume`、`停机` → **0 命中**。
同样也没有 fan-out 入口。

于是文档说"叫停批量任务看第七节"，但用户在界面上**无处可点**，
只能 curl 或者手建 `data/STOP` 文件（而后者按第 5 条还恢复不了）。

**建议**：控制台加一个明显的「🛑 停机」按钮（调 `/api/stop`）。

### 7.2 关于 #15 的补充说明

原报告说 `browser.save_session()` 写 2.2 MB storage state 也是同步 I/O —— **这条判断不成立**：
它走的是 `await ctx.storage_state(path=...)`，落盘由 Playwright 自己的 driver 进程完成，
不占 Python 事件循环。真正的同步大文件 I/O 只有 `usage.json`（每次调用整读整写），已修。

### 7.3 体检器 F3 的已知误报

`version: "1.0.0"`（带引号）会被报 F3「非 semver」，但 F8（闸门项）却接受 ——
根因是体检器自身两处口径不一致：

```python
# audit.py:424  F3：没 strip 引号 → 带引号必假报
ver = fm.get("version", "")
A.check(bool(re.match(r"^\d+\.\d+\.\d+", ver)), "MINOR", "F3", ...)

# audit.py:456  F8：strip 了引号 → 带引号能过
if ver:
    A.check(bool(VERSION_STRICT_RE.match(ver.strip("\"'"))), "BLOCKER", "F8", ...)
```

处理方式：`version` 写成**不带引号**的 `1.0.0` —— 两条都过，账面 100 分。
（`1.0.0` 不是合法数字字面量，YAML 会当字符串，安全。）

### 7.4 顺手做的两件打包卫生

1. **启动器加 `-B`**：`启动服务.bat` / `后台启动.vbs` / `install.py` 打印的 MCP 片段
   都给 python 加了 `-B`（不写 `.pyc`）。技能目录是要打包分发的，字节码缓存属运行期产物，
   不该落在里面 —— 实测带 `-B` 启动后技能目录 `__pycache__` 计数稳定为 0。
2. **`install.py` 的 MCP 片段改成 `json.dumps()` 生成**：手写字符串拼 JSON 一旦多逗号
   或塞注释就变成非法 JSON，用户照抄会把整份配置弄坏；改成从 dict 生成，天然合法。

### 7.7 收尾后复查又抓到两个「看起来通过」的坏工具（同日）

体检器给 100 分之后，我不满足于"闸门过了"，又去真机把**没验过的两条链**补上，
结果在 `tools/` 里翻出两个和 #5/#7 同族的缺陷 —— **体检器完全看不见，
因为它们既不是语法错误也不是打包问题，只在真正运行时才现形。**

这两条的共性值得单列：**「看起来通过」比「明确报错」更贵**。
报错会逼你去查；假通过会让你以为已经查完了。

#### ① `tools/mcp_probe.py` 会永久卡死，且一个字都不输出

```python
while time.time() - t0 < deadline and len(lines) < 12:
    line = proc.stdout.readline()          # ← 阻塞调用，没有超时
```

`readline()` 阻塞到有行为止，而 `deadline` 只在**两次读之间**才重新判断。
桥一共只吐约 5 行，读完之后第 6 次 `readline()` 永久阻塞，循环条件再也轮不到 ——
`deadline` 形同虚设。更坏的是结果**攒到 `proc.terminate()` 之后**才统一打印，
所以症状是**零输出被杀**，看着就是"桥挂了"。

**实测后果**：我第一次跑它得到"无输出 + 被 SIGTERM"，差点就去查 MCP 桥了；
换个带诊断的脚本一跑，桥**完全正常**（8 个工具、真实返回 541 字）。

另有两个同源隐患：
- `stderr=subprocess.PIPE` 开了却没人读 → 桥往 stderr 写多了会填满管道，**双向死锁**。
- `判定: FAIL` 时函数返回 `None`，**退出码仍是 0**，脚本/CI 会误判成功。

修法：stdout/stderr 各起一个读线程排进队列；每一步单独限时；**每完成一步立刻打印**
（真卡住时能一眼看出卡在哪步）；`sys.exit(handshake())` 让失败退 1。
反向验证：把预期的工具清单里塞一个不存在的名字 → 如期 `✗ 少了这些预期工具` 且返回 1。

#### ② `tools/selfcheck.py`：打印了会误导人的数字、临时 profile 不清理、失败仍退 0

- 它用一个**一次性的空 profile**（未登录）去开 `chat.deepseek.com`，所以
  `textarea=0 contenteditable=0` 是**必然**的；但它把这个数字原样打印出来，
  旁边还写着 "OK"，用户会合理地把 `0` 读成"输入框都找不到，肯定坏了"。
  → 加了说明：这几个计数不表示站点可用，登录状态请看控制台。
- `data/profiles/_selfcheck` 这个临时 profile（几百 MB 级）**用完从不删除**。
  → `finally` 里 `shutil.rmtree(..., ignore_errors=True)`。
- 两种模式**都失败**时 `main()` 仍返回 `None` → 退出码 0。
  → `return 0 if (ok1 or ok2) else 1`，并且 `sys.exit(asyncio.run(main()))`。
