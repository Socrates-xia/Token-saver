用户要求：**用 DeepSeek 的 HTTP 通道、豆包的 turbo 生图、Kimi 的追问、
元宝的意外关窗**，试一下这个技能的多端同时处理能力。

## 二、逐项实录

### ① DeepSeek 纯 HTTP 直连

```
提问前 running = []
via      = http直连(无浏览器)
elapsed  = 1.92 s
answer   = 在有序数组中每次折半缩小范围找目标。
提问后 running = []          ← 全程没打开过浏览器
```

`running` 前后都是空是这条最有力的证据：**只走 HTTP，一个窗口都没开。**
请求前会先从 `data/state/deepseek_http.json` 读登录态（Cookie + Bearer）。

### ② 豆包 turbo 生图

```
via     = input:div[contenteditable='true'] +button → dom +4图
elapsed = 37.84 s
images  = 4 个文件 → data/images/doubao-*.png
```

4 张 2048×2048 PNG，逐个校验了文件头与 `IHDR` 尺寸，是真图。
`+4图` 是 `via` 字段里的计数标记。

### ③ Kimi 追问

```
第1轮  prompt=请记住这三个数字：3、7、11
       via=… +enter → dom [清弹窗:round1:heuristic#1]   16.13s   answer='记住了'
第2轮  prompt=我刚才让你记的第二个数字是几
       continued=True  reused_page=True  context_turns=0   7.75s   answer='7'
```

第 2 轮比第 1 轮快一倍，因为 `context_turns=0` —— **页面还在同一个会话，直接接着问、
没有重发历史**（这正是省 token 的设计）。
顺带验证了弹窗自动清理在 Kimi 上生效（`[清弹窗:round1:heuristic#1]`）。

### ④ 元宝意外关窗自愈

模拟"用户直接关掉浏览器窗口"：找到元宝 profile 的 Edge 主进程 `pid=28652`
（先确认同机还有 26 个属于**用户自己 Edge** 的进程，绝不能误伤），
只杀元宝那一棵树 —— 杀之前 7 个进程，杀之后 0 个，而豆包+kimi 的 17 个进程毫发无损。

**此时网关内存里仍然认为元宝活着**，立刻发追问：

```
[alive]  pid=yuanbao 页面确实已关闭 → 判失效
[ctx]    pid=yuanbao 重建浏览器上下文（页面被关或失效）
[session] 已回填 yuanbao 登录态（20 个 cookie）
[thread] 续聊 yuanbao: 复用页面会话=False | ctx重建=True
         | prev='/0Qsn7mBALKq' cur='t/naQivTmsDa' | 回填历史兜底
```

返回：

```
ok=True   continued=True   reused_page=False   context_turns=1   elapsed=15.19s
answer = '7'          ← 上文是关窗之前交代的，说明历史确实补回来了
```

`reused_page=False` + `context_turns=1` 正是自愈的特征签名：
**复用不了页面 → 回填 1 轮历史 → 答案照样正确。**

## 三、抓到的 bug：生图会把上一轮的图当成这一轮的结果

### 现象

连续两次**不同**提示词的生图请求（都走"复用页面会话"，即不带 `reset`），
抓回来的 4 张图**逐张 SHA256 完全相同**：

```
第1轮（画一只奶龙） vs 第3轮（画一只橘猫）
  1066ca7f16ef6557  1066ca7f16ef6557   完全相同 ←
  1b74366dc6408163  1b74366dc6408163   完全相同 ←
  052e9197ac8a4abe  052e9197ac8a4abe   完全相同 ←
  699f96f276ced108  699f96f276ced108   完全相同 ←
```

而返回值是 `ok=true`、`images` 有 4 个、`via` 带 `+4图` —— **看起来完全正常**。

### 根因

`extract_images()` 原本是「把页面上所有 `naturalWidth/Height ≥ 512` 的 `<img>`
按面积排序取前 6」，**没有"这轮的图"这个概念**。豆包的图生成后留在 DOM 上不消失，
所以只要复用页面会话，历史消息里的旧图就会被重新下载一遍。

### 修法

1. 发问前先拍基线 `img_baseline` = 页面上现有的全部图片 URL（`limit=500`，必须**收全**）。
2. 抓图时排除基线里的图。
3. **排除必须在 `slice(0, limit)` 之前做**（写在 JS 里）。

第 3 点是修的过程中自己踩出来的：第一版是"JS 先取前 6、Python 再排除"，
结果页面上旧图一多，新图就被挤出前 6，返回空数组 —— 表现为"这轮没生成图"。
真机上表现为 `via = … 无新图(页面仅剩 8 张旧图)`。

另外把"没抓到新图"这件事**写进 `via`**：
`无新图(页面仅剩 N 张旧图)` / `无图`。以前是静默返回 `images=[]`，
调用方不知道是"没生成"还是"没抓到"。

### 回归测试

新增 `tools/selftest_grab_images.py`（12 项，用 canvas 造的本地假图，**不联网不登录**）。

关键设计：造 **8 张更大的旧图 + 2 张较小的新图**。
- 旧实现：JS 按面积取前 6（**全是旧图**）→ 再排除 → 返回 **0** ❌
- 新实现：JS 先排除旧图 → 再取前 6 → 返回 **2** ✅

**旧图数量必须超过 `limit`**，否则旧实现也能碰巧通过，测不出这个 bug。

反向验证过：把代码临时改回旧顺序，两条 ★ 断言如期变红（`得到 0`）、退出码 1；
恢复后 12/12 全绿。

### 真机复验

修完重启网关，连续两轮不同提示词（企鹅 / 老虎），都走复用页面会话：

```
第1轮  via=… +1图   哈希 ['79fd3f82e2d3']
第2轮  via=… +1图   哈希 ['1946b7792097']
重复 = 0 张 ✅
```

另外验证**没有少抓**：明确要"画 4 张不同姿势的柴犬"→ 拿到 4 张、哈希各不相同。
（单张请求只出 1 张，是豆包自己的行为，不是抓漏。）

## 四、一个冷启动残留（不算 bug，但值得知道）

浏览器刚打开、profile 停在上一轮旧会话上时，如果这一轮**助手只出图、没有文字**，
答案抽取器会退回到页面上残留的旧文字容器，于是 `answer` 字段可能拿到一段
与本次提问无关的旧文本（例如上一轮回填历史时留下的前言）。图本身是抓对的。

复现条件：冷启动 + 旧会话有文字 + 本轮纯图无文字。
规避：生图时带 `"reset": true`，或先发一句文字问句把页面"顶"到新会话。

**未修**（属于边缘情况，且改动会影响所有站点的答案抽取，风险大于收益）。

（`auto-<站点>`）关窗后追问会按设计**干净开局**、不接旧上文。

用点名话题 `db-追问关窗-1001`，三问一问比一问更依赖上文：

| 轮 | 提问 | 关窗时机 | `reused_page` | `context_turns` | 答案 | 耗时 |
|---|---|---|---|---|---|---|
| 1 | 请记住这三个数字：7、12、25 | — | False | 0 | `记住了` | 13.54 s |

三问全对。第 2 问的 `context_turns=1` 就是兜底生效的证据：新会话里没有上文，

不重发历史"的正常态（8.41 s，比回填那轮还快）。

网关日志：

```
[session] 已回填 doubao 登录态（55 个 cookie）

         prev='140710422018' cur='ao.com/chat/' | 回填历史兜底
```

### 踩出来的一个观测陷阱

`/api/providers` 的 `running` 字段**不能用来判断窗口是否还在** ——
`BrowserManager.running()` 就是 `list(self._ctx.keys())`，读的是**本地缓存句柄**，
不做存活探测。用户关掉窗口后它照样报 `true`（实测确认）。要确认窗口状态得看进程：

```powershell
Get-CimInstance Win32_Process -Filter "Name='msedge.exe'" |
  Where-Object { $_.CommandLine -like '*token-saver*profiles*doubao*' }
```

顺带又一次确认**没有误伤用户自己的 Edge**：匹配 `.token-saver\profiles\doubao`
的进程归零时，同机另 9 个 `msedge.exe` 全是用户本人的
（`AppData\Local\Microsoft\Edge\User Data`）。

### 账本核对

`threads.json` 里该话题 3 轮，答案依次 `记住了` / `12` / `25`（长度 3/2/2 字），
**0 轮含回填块痕迹** —— 没有出现"我方发出去的整段文本被当成答案"那类脏数据。

## 七、闲置自动关窗（v1.0.2）

用户的原话是：

> 你调用这个 skill 后，如果不需要再次与网页对话，能不能自动关闭。
> 每次调用完还需要我手动关闭网页。如果有继续追问的需要再保持网页开着，
> 确认不需要调用了那就把网页关了。

三句话拆成三条判据：**① 用完自己关；② 还要追问时别关；③ 关掉不等于停服务。**
实现是 `BrowserManager.close_idle()` + `server._idle_watchdog()`，配置项
`runtime.idle_close_seconds`（默认 180，`0` = 关掉该功能）。

### 真机四步实录（豆包）

| 步骤 | 做法 | 观测 |
|---|---|---|
| ① 开窗 | `/api/ask` 问豆包 | `running=["doubao"]`，`idle_for={"doubao":0.3}` |
| ② 晾着 | 什么都不做，过一会儿再读 | `idle_for={"doubao":51.2}`，窗口还在 |
| ③ 追问 | 同一站点再问一次 | `idle_for` 回到 `0.3`，窗口**没关**（9.01 s，复用会话） |
| ④ 用完了 | 不管它，继续等 | 日志 `[idle] pid=doubao 已闲置 184s → 自动关闭窗口`；`running=[]`、`auto_closed={"doubao":…}` |

第 ③ 步是"还要追问就别关"的直接证据：计时从 51.2 s 被续回 0.3 s ——
**追问本身就相当于"我还在用"**，不需要额外的 keep-alive 调用。

第 ④ 步之后按 `msedge.exe` 命令行筛 `token-saver`：**0 个**
（同机 9 个 `msedge.exe` 全是用户自己那份 `User Data`，未被误伤）。

### 手工关：`POST /api/close`

```bash
curl -X POST http://127.0.0.1:8787/api/close                      # 全关
curl -X POST http://127.0.0.1:8787/api/close -d '{"provider":"doubao"}'
```

实测返回 `{"ok":true,"closed":["doubao"],"running":[]}`，服务仍在跑；
紧接着再问一次，13.36 s 拿到答案，日志是

```
[ctx] pid=doubao 首次启动浏览器
[session] 已回填 doubao 登录态（55 个 cookie）
```

—— **关窗不影响登录态**，下次调用自动重开（只多花几秒）。

### 一个必须盯住的副作用：别把自己关成"停机"

`killswitch.note_rebuild()` 有条规则：**60 秒内浏览器被重建满 3 次 → 判定用户想停
→ 自动停机**。要是自动关窗也被算进这个计数，那么"闲置关掉 → 下轮重开 → 又关掉"
来回几次就会把网关停掉，而且用户完全不知道发生了什么。

核对结论：**不会触发**。触发条件是 `context()` 里 `self._page.get(pid) is not None`
（句柄还在、但页面死了 = 真·重建）；而 `close()` 会 `self._page.pop(pid, None)`，
所以关窗后的下一次是 `首次启动` 而不是 `重建` —— 上面日志里两处
`[ctx] … 首次启动浏览器` 就是实证。**用户自己手动关窗**那条路径不受影响，
仍照旧计数（句柄还在缓存里、没走 `close()`）。

### close_idle 的三条安全线

改这个函数之前先跑 `tools/selftest_idle.py`（25 项），它把这三条钉住了：

1. **正在提问的站点绝不关** —— 而且只读 `lock.locked()`，**不去 `await` 拿锁**。
   否则巡检会卡在第一家正在跑的站点上，后面所有站点这一轮都不巡检了
   （用例里用 `asyncio.wait_for` 卡了 2 秒上限）。
2. **没有计时记录的先记成"刚用过"再跳过** —— 不然刚建出来的上下文会因为
   "从没见过"被立刻收掉。
3. `idle_seconds <= 0` → 整个功能关闭，直接返回。

顺带一条：计时刷新点放在 `_try_one()` **问完之后**，不是 `ensure_page()` 那一刻 ——
一次提问可能跑几十秒，从"问完"起算才准。HTTP 直连路线在上面就 `return` 了，
不会走到这里，**它没开浏览器就不该替某个闲置窗口续命**（这条也有断言 + 源码契约检查）。

## 八、HTTP 直连被叫停：日志撒谎与修复（v1.0.3）

起因是一个提问：「如果 deepseek 走的是 http 模式，我看不到窗口，那我想停止的时候该怎么办？」
—— 这个问题本身指向一个真实的盲区：**"没有窗口可关"很容易被误读成"停不下来"**。

### 真机复现（修之前）

走直连问一句长回答，**7 秒后** `POST /api/stop`。结果三件事同时成立：

| 观察点 | 实际值 |
|---|---|
| 流有没有被掐断 | **断了** —— 错误信息写着"用户在**生成过程中**叫停了本次调用" |
| 客户端拿到什么 | `{"ok":false,"error":"[已停机] …","hint":"…POST /api/resume…"}` |
| 网关日志写什么 | `[http] 直连失败 → 退回浏览器：HttpError: [已停机] …` ← **撒谎** |

第 3 行是问题所在。所谓"直连失败"其实是"用户按了停机"，而"退回浏览器"更没发生
（`/api/status` 的 `running` 全程是空的，日志里一行 `[ctx]` 都没有）。
**看日志的人会跑去查 HTTP 通道、查凭证、查 PoW，而真正的原因只是他刚按了停机。**

### 根因

`_stream_completion` 里命中停机时抛的是**普通 `HttpError`**：

```python
if should_stop and should_stop():
    raise HttpError("[已停机] 用户在生成过程中叫停了本次调用")
```

而 `HttpError` 的语义是"HTTP 层面失败，调用方退回浏览器"（见该类 docstring）。
于是 `adapter_deepseek.ask_http` 那个 `except Exception` 顺手把它吞成了
"这条路走不通"，`pool` 再退回浏览器（虽然停机闸会把 `ensure_page` 挡下，
所以没白开窗口，但日志已经撒完谎了）。

一句话：**"用户叫停"和"通道故障"共用了一个异常类，而它们的处置完全相反**
（一个该立刻收手，一个该换路重试）。

### 修法：给"叫停"一个自己的异常类

| 位置 | 改动 |
|---|---|
| `core/http_deepseek.py` | 新增 `HttpStopped(HttpError)`；`_stream_completion` 命中停机时改抛它 |
| `core/adapter_deepseek.py` | 在 `except Exception` **之前**加 `except http_deepseek.HttpStopped: raise`（原样抛出） |
| `core/pool.py` | `_try_one` 里 `except HttpStopped as e:` → 直接按停机收手返回，**不退回浏览器** |

顺序依然是全部：`HttpStopped` 那一支必须排在 `except Exception` **之前**，
否则又被吞掉 —— 和之前 `looks_like_echo` 那次的教训一模一样
（**判据/分支的顺序就是语义**）。

修后同一场景：

```
# 客户端
{"ok":false,
 "error":"[已停机] 用户在生成过程中叫停（修后复验）",
 "attempts":[{"provider":"deepseek","ok":false,
              "error":"[已停机] 用户在生成过程中叫停了本次调用"}]}
# 日志
[http] deepseek 被叫停（生成中停机，连接已断开）
```

`attempts[0].error` 里那个 `RuntimeError: ` 前缀也一起没了 ——
它原来是从浏览器路径包出来的，等于把"走错路"的痕迹写进了错误信息。

### 回到那个提问：直连模式到底怎么停

| 方式 | 效果 |
|---|---|
| `POST /api/stop` / 控制台「■ 叫停全部」 | **推荐**。当前流立刻断，后续调用秒级被拦，随时 `/api/resume` 复工 |
| `POST /api/shutdown` | 连网关一起关，当前请求随进程死掉；彻底，但要重新起服务 |
| 调用方不再发下一问 | MCP 场景最常见；正在跑的那一问会自己结束 |

**"没有窗口" ≠ "停不下来"**，也**没有"等它答完"这一说** ——
停机是在 SSE 逐行读取的循环里查的，模型吐到一半就能掐。

### 踩到的两个自伤

1. **校验命令自己失效**：用 `grep -c $'\r' file` 查行尾，在 Git Bash 里
   `$'\r'` 被吃成了**空模式**，于是"所有行都算 CRLF"、`grep -vc` 恒为 0 ——
   看起来像"文件全是 CRLF"，其实什么都没测。改用逐字节统计才发现本包
   **26 个纯 CRLF / 37 个纯 LF**（`core/http_deepseek.py`、`tools/*.py` 是 LF；
   `core/pool.py`、`core/adapter_deepseek.py`、`SKILL.md` 是 CRLF）。
   补丁脚本因此改成**按文件自动识别**，不再硬编码猜测。
2. **新写的断言自己站不住**：源码契约断言用了全局
   `ad_src.index("except Exception as e:  # noqa: BLE001")` 比先后，
   而这个文件靠前的 `harvest()` 里**也有一个**同名 except —— 于是拿到的是
   那一个，断言假红。改成**先定位 `await http_deepseek.ask(` 再在后续片段里比**。
   又一次印证：**假红和假绿一样费时间，断言的范围要和它想表达的语义对齐。**
